## 2. Задачи

### FIX-1 — Разделить «ветки нет» и «экспорт не удался» в бэкапе  [P0]

> **Статус: ✅ реализовано** (2026-09-18). `cleaner.py`: `_branch_exists()` +
> классификация `exported`/`failed`/`skipped`, fail-closed на существующих
> ветках, защита от fail-open в `delete_layout`. Unit-тесты:
> `test_review_regressions.py` (`TestBranchExists`,
> `TestBackupRegistryClassification`, `TestDeleteLayoutBackupGuard`).

**Факты.**
- Контракт объявлен fail-closed в двух местах: docstring `backup_registry`
  (`cleaner.py:358-363`) — «вызывающий код **обязан** проверить `failed` перед
  изменением реестра»; комментарий `delete_layout` (`cleaner.py:2036`) — «КРИТИЧНО:
  без полного бэкапа удаление НЕ выполняется».
- Реализация — fail-open: `cleaner.py:2048-2055` пишет warning и продолжает;
  `_wipe_branches()` выполняется. Полный провал (ни одной ветки) действительно
  отменяет удаление — `cleaner.py:471-478` бросает `BackupError`.
- `failed_branches` смешивает две разные ситуации:
  (a) ветки нет в реестре — бэкапить нечего, риск 0;
  (b) ветка есть, но `reg export` упал — реальная потеря данных.
- Проверено локально: `reg export "HKCU\Keyboard Layout\NoSuchBranchXYZ" f.reg /y`
  → `exit 1`, «Не удается найти указанный раздел или параметр в реестре».
  Существующие ветки (`Keyboard Layout\Preload`, `Keyboard Layout\Substitutes`,
  `HKEY_USERS\.DEFAULT\Keyboard Layout\Preload`) экспортируются с `exit 0`.
- Следствие: на «чистой» системе бэкап почти всегда помечается неполным, и
  пользователь видит `dlg_result_backup_partial` (`main.py:1533-1535`,
  `locales/ru.json:164`) — **ложная тревога**. Настоящий отказ экспорта выглядит
  в отчёте точно так же.
- Тестов на этот контракт нет: partial-путь не покрыт вообще, `backup_registry`
  покрыт только live-тестами (`test_sandbox.py:142-232`).

**Почему это дефект, а не стилистика.** Пользователю обещают откат, а гарантию
отката не проверяют. При этом сигнал о реальной потере данных неотличим от шума.

**Решение.**
1. Добавить в `cleaner.py` (рядом с `_paths_to_backup`, строка 211) хелпер
   `def _branch_exists(root: str, subkey: str) -> bool`:
   - `winreg.OpenKey(_ROOT_CONST[root], subkey, 0, winreg.KEY_READ)` → `True`;
   - `FileNotFoundError` → `False`;
   - `PermissionError`/`OSError` → **`True`** (пессимистично: считаем, что ветка
     может существовать, поэтому провал её экспорта будет признан реальным).
2. В цикле `backup_registry` (`cleaner.py:412-443`) ветку, которой нет, не считать
   провалом: писать в новый список `skipped_branches` (info-уровень, не warning).
   Экспорт для отсутствующей ветки не вызывать.
3. `report` получает три ключа: `exported`, `failed` (только реальные отказы),
   `skipped` (нет ветки). Обновить docstring `cleaner.py:358-363`.
4. Изменить семантику `BackupError`: бросать, если **хотя бы одна существующая**
   ветка не экспортирована (сообщение — перечислить ветки). Это делает комментарий
   `cleaner.py:2036` правдой и не требует новых locale-ключей: GUI уже показывает
   `dlg_backup_failed` с текстом ошибки (`main.py:1533`, `locales/ru.json:163`).
5. В `delete_layout` (`cleaner.py:2048-2055`) оставить защиту: если по какой-то
   причине `failed` непуст — **прервать** операцию (вернуть результат с
   `backup_ok=False`), а не продолжать. Добавить в отчёт
   `backup_skipped_branches: list[str]`.
6. `main.py:1533-1535`: не считать `skipped` проблемой. Новых locale-ключей не
   требуется — достаточно не показывать предупреждение.

**Критерии приёмки.**
- Отсутствие ветки в реестре не порождает `BackupError` и не показывает
  предупреждение в GUI.
- Провал экспорта существующей ветки → `BackupError`, `.reg` не создаётся,
  `delete_layout` возвращает `backup_ok=False`, реестр не изменён.
- В отчёте различимы `exported` / `failed` / `skipped`.
- Порядок «бэкап → подтверждение → мутация» не нарушен ни в одном сценарии.

**Тесты (unit, без live-реестра).**
- Фикстура: `conftest.FakeWinreg` (`OpenKey` для отсутствующего ключа бросает
  `FileNotFoundError` — `conftest.py:108-113`) + подмена `cleaner.run_hidden`:
  мок разбирает `cmd` вида `["reg", "export", <путь>, <outfile>, "/y"]` и создаёт
  `<outfile>` в UTF-16 LE (тот же приём, что в `test_scanner.py:953-976`).
- Кейсы: (a) все ветки существуют, экспорт ок; (b) только отсутствующие ветки;
  (c) существующая ветка + `returncode=1` → `BackupError` и `*.reg` не создан;
  (d) смесь «ок + отсутствует» → файл создан, `failed == []`;
  (e) «ок + реальный отказ» → `BackupError`.
- Тест уровня оркестратора: `delete_layout` при `BackupError` → `backup_ok=False`
  и `_wipe_branches` не вызван (мок-счётчик).

**Риски.** Если удаление окажется невозможным из-за того, что `reg.exe` блокируется
antivirus/политикой, пользователь не сможет удалить раскладку. Это осознанный
размен: fail-closed вместо fail-open. Если такой сценарий реален — см. «Открытые
вопросы», п. 2.

**Оценка.** S (~20 строк кода + тесты). Самая дешёвая правка с наибольшим эффектом.

### FIX-2 — Бэкап должен покрывать `SettingSync\Groups\Language`  [P0]

> **Статус: ✅ реализовано** (2026-09-18). `cleaner.py`:
> `_SETTINGSYNC_GROUPS_SUBKEY` + `_settingsync_groups_key_path()`
> (sandbox-aware, см. FIX-2c) + `_settingsync_groups_paths()`;
> `delete_layout(..., block_cloud_sync=False)` собирает `paths_to_backup`
> с backup-only веткой и вызывает `disable_language_sync()` только при
> явном согласии (Находка A); GUI передаёт `self.block_sync_checkbox.get()`
> (main.py), CLI — флаг `--block-cloud-sync`. Тесты:
> `TestSettingsyncGroupsBackupOnly`, `TestDeleteLayoutCloudSyncOptIn`
> (`test_review_regressions.py`).

**Факты.**
- `delete_layout` вызывает `disable_language_sync()` **безусловно**
  (`cleaner.py:2101-2104`) и тот пишет
  `HKCU\Software\Microsoft\Windows\CurrentVersion\SettingSync\Groups\Language\Enabled=0`
  (`cleaner.py:1546`).
- В бэкап и в скан входит другая ветка — `...\SettingSync\Namespace\Language`
  (`scanner.py:258-263`, `cleaner.py:228-231`). `Groups\Language` не бэкапится
  и не сканируется вообще.
- `restore_backup()` (`cleaner.py:1834-1849`) делает только `reg import` +
  восстановление списка языков; `enable_language_sync()` не вызывается ни в GUI,
  ни в `restore_backup` (`main.py:1765-1772`, `1752-1772`).
- Следствие: после удаления и последующего восстановления в реестре остаётся
  `Enabled=0`, хотя до операции там было `1` или значения не было вообще.

**Находка A (нет в ред. 1).** Галочка `chk_block_cloud_sync`
(`gui_widgets.py:312-316`, инициализация `main.py:592`, обработчик
`main.py:1575-1596`) управляет **только** ручным тумблером. В `delete_layout(klid)`
(`main.py:1365`) её состояние не передаётся, и удаление блокирует облако даже
у пользователя, который этого не просил. Это нарушение opt-in, отдельное от
проблемы восстановления.

**Решение (две части).**
1. **Бэкап.** Держать `Groups\Language` как **backup-only источник**: не мутировать
   его через `_wipe_branches`, не показывать в dry-run, но сохранять в `.reg`.
   - В `cleaner.py` ввести `_SETTINGSYNC_GROUPS_SUBKEY` и
     `def _settingsync_groups_paths() -> list[dict[str, str]]`, вернуть
     `[{"root": "HKCU", "subkey": <путь>}]`.
   - В `delete_layout` (`cleaner.py:2032`) собрать
     `paths_to_backup = _paths_to_backup(...) + _settingsync_groups_paths()`.
   - **Не** добавлять эту ветку в `scanner._ORIGINAL_AFFECTED_BRANCHES`: иначе
     она войдёт в матрицу мутаций, в `_REPORT_FIELD`, в `_wipe_branches` и в
     `test_affected_branches_exact_composition` («ровно 6 источников»,
     `test_scanner.py:555-585`) — то есть приложение начнёт удалять `Enabled`
     как «совпавшее значение». Это неверно: состоянием управляет только API.
   - Инвариант-тест: backup-only источники никогда не попадают в `_wipe_branches`
     и в план (`plan_layout_removal`).
   - Побочный эффект, который надо задокументировать: если до удаления значения
     `Enabled` не было, после восстановления появится `Enabled=1` (это значение
     по умолчанию, поведение синхронизации эквивалентно).
2. **Согласие (Находка A).** Прокинуть решение пользователя в удаление:
   `delete_layout(layout_id, block_cloud_sync: bool = False)`; GUI передаёт
   `self.block_sync_checkbox.get()` (`main.py:1365`).
   При `False` шаг 4a пропускается (сейчас поведение «всегда блокируем»).
   Обратная совместимость CLI: добавить `--block-cloud-sync` в CLI `cleaner.py`
   (`2262-2273`), по умолчанию выключено.

**Критерии приёмки.**
- `.reg`-бэкап содержит секцию `HKEY_CURRENT_USER\...\SettingSync\Groups\Language`.
- Round-trip: удаление (`Enabled=0`) → restore → `Enabled` возвращается к
  исходному значению; `is_language_sync_blocked()` даёт то же, что до операции.
- Ветка `Groups\Language` не появляется в плане удаления и не удаляется

1. **Sidecar-манифест** `<backup>.manifest.json`: версия приложения, klid,

   `dlg_result_backup_partial`-стиль, при необходимости — один новый locale-ключ
   `dlg_result_plan_drift` в 6 файлов).
3. Документировать в `README.md`: `.reg` — самостоятельный путь восстановления;
   манифест — дополнительный аудит и расширенная диагностика.

**Критерии приёмки.**
- Манифест создаётся вместе с `.reg` и валиден как JSON.
- Расхождение план↔факт попадает в отчёт и в лог, а не теряется.

  поведение кода.
- На живой машине нумерованные ветки реально существуют:
  `HKCU\Keyboard Layout\Preload` — значения `1`, `2`;
  `HKCU\Software\Microsoft\CTF\SortOrder\Language` — `00000000 = 00000419`,
  `00000001 = 00000409`.
- Документально подтверждено только соглашение о нумерации: SIL («values `1`..n, one
  for each keyboard installed») и KB138354 («Beginning with Windows NT 4.0, the first
  keyboard layout in the list of available layouts is used by default» — то есть
  значение `1` задаёт раскладку по умолчанию). **Утверждение, что «дыра» приводит к
  отбрасыванию раскладок после неё, в документации Microsoft не найдено.**
- Внешнее ревью подаёт это как факт; в ред. 3 это гипотеза, требующая проверки.

**Решение.**
1. **Сначала верификация в VM** (Windows 10 и 11), без изменения кода: создать
   `Preload = {1: 00000419, 2: 00000409, 3: 0000040C}`, удалить значение `2`,
   выйти/войти → проверить `Get-WinUserLanguageList`, `GetKeyboardLayoutList` и
   переключение Alt+Shift. То же для `CTF\SortOrder\Language`.
2. Если гипотеза **не подтвердится** — закрыть задачу как «проверено, не воспроизводится»
   и не менять код: пере-нумерация сама по себе рискованна, так как меняет номер
   значения, а значение `1` определяет раскладку по умолчанию.
3. Если подтвердится — уплотнять с сохранением **порядка и семантики**:
   отсортировать оставшиеся значения по исходному числовому имени, переписать как
   `1..N`; значение, стоявшее первым, остаётся первым. Применять только к:
   `HKCU\Keyboard Layout\Preload`, `HKU\.DEFAULT\Keyboard Layout\Preload`,
   `HKCU\Software\Microsoft\CTF\SortOrder\Language`.
   **Не применять** к `Control Panel\International\User Profile\<язык>\KeyboardLayoutPreload`:
   там `REG_MULTI_SZ` с токенами `0809:00000809`, а не индексы.
4. Изменение нумерации — это мутация, поэтому она должна быть видна пользователю:
   строка в плане (если удаляется значение `1` — отдельное предупреждение «изменится
   раскладка по умолчанию») и поле в отчёте (`preload_renumbered`).

**Критерии приёмки.**
- Есть письменный результат VM-проверки (воспроизводится / не воспроизводится).
- При реализации: порядок раскладок сохранён, ни одно значение не потеряно и не
  resurrected; план и отчёт отражают уплотнение (инвариант §3).
- `User Profile\...\KeyboardLayoutPreload` не пере-нумеруется.

### FIX-13 — Закрытие окна во время операции оставляет ввод остановленным  [P0/P1]  ✅ реализовано

**Факты.**
- В `main.py` **нет** обработчика `WM_DELETE_WINDOW`: `protocol(...)` не вызывается
  ни разу (проверено поиском), при этом вся работа идёт в `threading.Thread(..., daemon=True)`
  (`main.py:886, 1331, 1370, 1772, 1835`), а завершение — `self.destroy()` (`main.py:1962`).
- `delete_layout` работает внутри `with CtfmonSuspender():` (`cleaner.py:2071`), и
  восстановление службы делает **только** `__exit__` (там вызывается `_start_ctfmon()`).
- Скрипт остановки — жёсткий: `Stop-Process -Name ctfmon -Force` и
  `Stop-Process -Name TextInputHost -Force` (`scripts/layout_cleaner_stop_ctfmon.ps1:15-16`).
- Следствие: крестик во время удаления → процесс завершается, daemon-поток убит,
  `__exit__` не выполнен → ctfmon и TextInputHost остаются остановленными.
  Уточнение к внешнему ревью: Windows обычно поднимает ctfmon при следующем входе и по
  требованию TSF, поэтому «до перезагрузки» — верхняя оценка; но состояние
  неопределённое и это ровно то, чего пользователь не ожидает от «безопасной» утилиты.

**Решение.**
1. Флаг `self._operation_in_progress` (устанавливать в `_after_plan`/`_start_restore`
   и снимать в `_after_delete`/`_after_restore`/`_after_delete_error`).
2. `self.protocol("WM_DELETE_WINDOW", self._on_close)`: при активной операции —
   сообщение «Идёт операция, дождитесь завершения» и **не** закрывать окно;
   иначе — штатное завершение.
3. Гарантия на случай аварийного выхода: `atexit`-хук и обработчик `SIGTERM`/`SIGBREAK`,
   вызывающие `_start_ctfmon()` (идемпотентно: если процесс уже запущен — no-op).
4. Файл-маркер «служба ввода остановлена» рядом с логом: при следующем старте приложения
   маркер найден → `_start_ctfmon()` + запись в лог (страховка от падения/`kill`).

**Критерии приёмки.**
- При активном удалении окно не закрывается; после завершения операции — закрывается.
- `atexit`-хук дергает `_start_ctfmon` (проверяется monkeypatch-ом).
- Маркер не остаётся после штатного завершения.

**Тесты.** unit: обработчик закрытия при `_operation_in_progress=True` не вызывает
`destroy` (spy) и показывает предупреждение; unit: `atexit`-хук вызывает `_start_ctfmon`
при установленном маркере; unit: маркер удаляется в `CtfmonSuspender.__exit__`.

**Оценка.** S–M.

### FIX-24 — Синхронизация списка языков не работала на живой системе  [P0]

> **Статус: ✅ реализовано** (2026-09-26). Найдено при проверке FIX-5/FIX-6,
> исправлено вместе с FIX-7/FIX-8. `layout_cleaner_cleanup.ps1`: элементы
> списка языков разворачиваются явно (`foreach ($item in (Get-WinUserLanguageList))`),
> раскладки вычищаются через `Clear()`/`Add()` на самом списке.
> Мок в `test_cleanup_powershell.py` приведён к настоящей форме
> (`return ,$list`); 3 новых регрессионных теста, один из них читает
> настоящий список языков и сверяет форму. Живая проверка:
> `cleaner.py <KLID> --plan` → `DRYRUN` + `tips_removed`, раньше `returncode=1`.

**Факты (проверено запуском на этой машине).**
- `Get-WinUserLanguageList` возвращает **один объект** типа
  `System.Collections.Generic.List<WinUserLanguage>`, а не поток языков:
  ```
  $list = Get-WinUserLanguageList
  $list.GetType().Name   ->  List`1
  $list.Count            ->  2
  ```
- Прежний код `$langs = @(Get-WinUserLanguageList)` давал **массив из одного
  элемента — сам список**. Дальше `foreach ($l in $langs)` выполнял ровно одну
  итерацию, где `$l` — список, а не язык:
  - `$l.LanguageTag` → member-enumeration склеивает теги: `"ru en-US"`;
  - `$l.InputMethodTips` → склеивает раскладки всех языков: `System.Object[]`.
- Правка `$l.InputMethodTips.Remove($tip)` на таком объекте падала
  `MethodInvocationException` («метод Remove не найден»). С `$ErrorActionPreference
  = 'Stop'` скрипт уходил в ошибку на **последнем** шаге, **не применяя
  изменений**: `Set-WinUserLanguageList` не вызывался. То есть шаг 4
  `delete_layout` («синхронизация списка языков») не работал ни на одной
  системе, а отчёт честно показывал `returncode=1`.
- Свойство `InputMethodTips` у `WinUserLanguage` — **только для чтения**
  (присваивание → `RuntimeException`); мутабелен сам список `List<string>`.
  Именно поэтому `New-WinUserLanguageList` (restore.ps1) работает: там
  `Clear()`/`Add()` применены к правильному типу.
- **Почему тесты это пропускали:** мок отдавал два отдельных `pscustomobject`
  вместо одного списка, поэтому `@(...)` корректно разворачивал его в два
  элемента и `foreach` видел языки. Мок был удобнее реальности — и делал
  функцию «зелёной» при полностью нерабочей. Это тот же класс дефекта, что
  разбирает FIX-7: расхождение формы данных и источника истины.

**Решение.**
1. Разворачивать список явно: `foreach ($item in (Get-WinUserLanguageList))`.
2. Раскладки не удалять вызовом метода и не присваивать read-only свойство,
   а пересобрать список через `Clear()`/`Add()` (работает и для `List`, и для
   массива).
3. Привести мок к настоящей форме (`return ,$list`) и закрепить форму
   тестом, который читает реальный `Get-WinUserLanguageList`.

**Критерии приёмки.**
- `python cleaner.py <KLID> --plan` на живой системе: `available: True`,
  `DRYRUN`, заполнен `tips_removed` — не `returncode=1`.
- Тест краснеет при возврате `$langs = @(Get-WinUserLanguageList)` и при
  присваивании `InputMethodTips`.
- Мок в тесте совпадает с формой, возвращаемой настоящей командой.

**Оценка.** S (правка скрипта) + S (тесты).

## 7. Спорные и опровергнутые утверждения (в т.ч. из внешнего ревью)

**Опровергнуто (проверено запуском/поиском):**

- **«Мёртвая ветка `k.isdigit() and k[0] != "0"` в `_klid_variants» (внешнее ревью,
  2.6).** Неверно. Это путь десятичной записи HKL:
  `_klid_variants("67699721")` → `{'04090409', '1734973217', '67699721'}`.
  Ветка достижима (CLI/API принимают и KLID, и HKL — обе формы проходят
  `re.fullmatch(r"[0-9a-f]{8}")`), а её удаление сломало бы обработку HKL-формы.
  Исправлено: механизм сопоставления всё равно требует переработки — см. FIX-22.
- **«CTF сопоставляется через десятичный LANGID из `variants`» (там же).** Неточно:
  CTF вычисляет HKL как `(LANGID из имени ключа 0x???????? << 16) | base_low`
  (`cleaner.py:986-998`). Проверено на живой структуре: `Assemblies\0x00000419\{GUID}`
  → `KeyboardLayout = 68748313`, `SortOrder\AssemblyItem\0x00000409\{GUID}\00000000`
  → `67699721`. Ложное срабатывание в CTF возможно только через точное равенство
  «голому» десятичному значению, а не через сам механизм пересчёта.
- **«Windows читает `Preload` последовательно от 1, дыра отбрасывает остальные
  раскладки» (внешнее ревью, 1.2).** Не подтверждено: ни Microsoft Learn, ни KB138354,
  ни SIL-документ не описывают усечение списка при пропуске номера. KB138354
  подтверждает только, что значение `1` задаёт раскладку по умолчанию. Механика
  отсутствия уплотнения в коде — факт; потеря раскладок — гипотеза. Оформлено как
  FIX-12 с обязательной VM-проверкой.
- **«Переход на onefile сломает поиск ресурсов молча» (внешнее ревью, 2.7).**
  Не доказано: PyInstaller задаёт `__file__` модулей внутри `sys._MEIPASS`, куда
  распаковываются и data-файлы. Реальный риск — реструктуризация (FIX-10/11),
  поэтому хелпер нужен как предпосылка, а не как исправление наблюдаемого дефекта.
- **«Сообщение об ошибке для первой проблемной ветки может не залогироваться»
  (внешнее ревью, 2.2).** Неточно: ветка, упавшая с исключением, логируется в
  `except` (`cleaner.py:431`); условие `cleaner.py:435` подавляет дубликат.
  Настоящий дефект — только неверная классификация «экспортирована» (FIX-16).

**Уточнено по масштабу:**

- **«259 тестов, из них 26 живых»** → фактически **281** собранный тест: 255 unit + 26 live.
- **«`Copy-UserInternationalSettingsToSystem` только для Windows 11 / Server 2022»** →

  микросекунды есть (`cleaner.py:398`, коммит `80c5f81`). Осталось как FIX-9 (P3).
- **«CJK mapping: `ko-KR` → `00001008`» (пункт 6 ред. 1).** Недействительно: строки в
